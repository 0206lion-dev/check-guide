## 3. 왜 그렇게 설계했나 (Why)

**조회 기능을 직접 구현하지 않고 파인(FINE) 경로만 안내한 이유.** 제도권 금융회사 조회, 대부업체 등록조회, 유사투자자문업자 조회는 이미 금감원 파인이 공식 제공하는 기능이다. 이를 스크래핑하거나 재구현하면 (1) 조회 결과가 원본과 어긋날 경우 법적·신뢰성 문제가 생기고, (2) 대부업체 조회는 `type_profiles.json`에 기록된 대로 외부 시스템(`fines.fss.or.kr`)으로 연결되는 구조라 재구현 자체가 이중 작업이다. 서비스의 가치를 "조회 대행"이 아니라 "어디를, 왜, 어떻게 확인해야 하는지 판단해주는 안내"로 좁힌 것은 처음부터의 설계 방향이었다(`index.html` 안내 문구, `buildReason`/`buildJudgment` 함수의 존재 자체가 이를 뒷받침).

**규칙 기반을 먼저 만들고 LLM을 나중에 얹은 이유.** 이번 세션은 사용자의 "규칙 기반은 완성됐으므로 그 위에 보정 레이어만 얹는다"는 명시적 지시로 시작했다. 규칙 기반이 먼저 완성돼 있어야 하는 이유는 6장에서 검증하듯 LLM 계층 전체가 실패해도(API 키 없음, 429, 타임아웃) 서비스가 죽지 않게 하기 위함이다 — LLM은 "위에 얹는" 보정일 뿐 판정의 필수 경로가 아니다.

**LLM에게 URL·건수 생성을 금지한 이유.** `analyze.js`의 시스템 프롬프트(23~41행)에 "URL이나 메뉴 경로를 새로 만들지 마세요", "건수나 비율을 계산하지 마세요"를 명시했다. LLM은 확률적으로 그럴듯한 URL이나 통계를 지어낼 수 있는데(hallucination), 이 서비스는 "금감원 소비자경보 198건 분석"이라는 근거 위에 서 있으므로 근거 없는 수치나 실재하지 않는 URL이 하나라도 섞이면 전체 신뢰도가 무너진다. 확인 대상 목록도 LLM이 새로 만들지 못하게 했다 — 목록은 `type_profiles.json`의 실측 데이터(`fine_menu_paths`)에서만 나와야 한다.

**실시간 조회 API 연동을 하지 않은 이유.** `type_profiles.json`을 보면 두 가지 근거가 남아 있다. 첫째, 여러 확인 대상의 `url` 필드가 `"확인필요"`로 비어 있고 `출처`에 "이번 조사에서 확인 못함"이라고 명시돼 있다(예: P2P 등록조회, 해외 비상장주식 상장·공시 여부). 둘째, 가상자산사업자 신고 여부 항목의 `출처`에는 "kofiu.go.kr 직접 접속이 세션 중 오류 페이지를 반환해 게시물의 정확한 URL은 확인하지 못했다"는 기록이 있다 — 즉 자동 조회 자체를 시도했으나 대상 사이트가 안정적인 API나 고정 URL을 제공하지 않아 실패했다는 뜻이다. 공식 API가 없는 상태에서 스크래핑으로 우회하면 이용약관 위반 소지와 사이트 구조 변경 시 유지보수 부담이 생기므로, 공모전 기간 내에는 "직접 확인 안내"로 좁힌 것이 합리적인 선택이었다고 판단한다(단 8장에서 남은 과제로 재론한다).

## 4. 어떻게 만들었나 (How)

### 판정 파이프라인 (`app.js`)

```
입력 텍스트
  └─ detectSignals(text)                     [148~184행]
       ├─ detectDataBackedSignals(text)       signals.json 24종 원문/동의어(signal_synonyms.json)/숫자 패턴(%) 매칭
       └─ detectPatternSignals(text)          PATTERN_SIGNALS 5종 — 정규식 기반, 경보 원문 인용(24~93행)
  └─ determineType(matchedSignals, text)      [218~271행]
       ├─ signalTotals: dataBacked 신호는 by_type 건수 합산, 패턴 신호는 leanType에 weight 합산
       ├─ keywordFallbackScore(text)          신호 0건일 때의 일반 키워드 폴백 [186~202행]
       └─ 신호 기준 유형과 키워드 기준 유형이 다르고 키워드가 2건 이상 우세하면 키워드로 보정
  └─ pickChecks(type)                         [285~302행] URL 있는 항목 + 탐색절차 있는 항목만 채택(최대 3개)
  └─ buildReason() / buildJudgment()          [362~390행] 확인 대상별 법적 근거·판단 기준 차등 제공
  └─ renderSimilarAlerts(type, signalNames)   [552~592행] 겹치는 신호 우선, 0건이면 최근 경보로 대체
```

### 규칙 층과 LLM 층의 역할 분리

- **규칙 층** (`detectSignals` ~ `renderSimilarAlerts`, `runAnalysis` 672~685행): 신호 탐지, 유형 판정, 확인 카드, 유사 사례를 모두 계산하고 즉시 화면에 렌더링한다. LLM 호출 여부와 완전히 무관하게 끝난다.
- **LLM 층** (`runAnalysis` 687행 이후, `analyze.js` 전체): 규칙 층이 이미 그린 화면 위에 "상황 요약"과 (필요시) "유형 보정 안내"만 별도로 추가한다. LLM은 규칙 층이 만든 `typeResult.type`, `matchedSignals`, `pickChecks()` 결과를 입력으로만 받고, 그 값을 바꿔 쓰지 않는다 — `analyze.js` 프롬프트가 확인 대상 목록·URL·건수 생성을 금지하는 것도 이 경계를 지키기 위함이다(3장).

### 폴백 동작

`fetchLlmAnalysis`(640~659행)는 네트워크 오류든 HTTP 오류든 무조건 `{ok:false}` 형태의 객체를 반환하고 절대 예외를 던지지 않는다. `runAnalysis`는 이 결과를 받아 `llmResult.ok`가 아니면 `renderQuotaNotice()`(429인 경우) 또는 `clearSummary()`(그 외 모든 실패)만 호출한다 — 규칙 층이 이미 렌더링한 신호·유형·확인 카드·유사 사례에는 어떤 코드도 손대지 않는다.

## 5. 시행착오와 수정

### a) 페르소나 3개가 위험 신호 0건으로 나온 문제

- **발견**: 페르소나 3종의 시나리오 원문(`personas.json`)으로 `detectSignals`를 돌리면 `signals.json`의 24종 신호가 하나도 안 걸렸다.
- **원인 분석**: `signals.json`의 신호명은 금감원 보도자료 문체 어휘("사칭", "고수익", "미신고" 등)인데, 페르소나 시나리오는 일반 사용자의 구어체 문장("국내 증권사가 아니라 처음 보는 곳에서 판매한다")이라 정확히 일치하는 문자열이 없었다(`app.js` 150행 주석: "signals.json 원문 어휘 + 동의어 사전 + 숫자 패턴까지 포함해 매칭한다").
- **왜 문제인가**: 신호가 0건이면 유형 판정도, 확인 카드 근거도 만들 수 없어 서비스의 핵심 기능이 작동하지 않는다.
- **어떻게 고쳤나**: `signal_synonyms.json`을 신설해 신호별 구어체 동의어 목록을 만들고, `detectDataBackedSignals`(152~166행)가 원문 일치 다음으로 동의어 일치를 검사하도록 했다. 예: `"무인가": ["국내 증권사가 아니", "처음 보는 곳에서 판매", ...]`.
- **왜 LLM으로만 메우면 안 되었는가(안정성 설계)**: 동의어 매칭을 LLM에 맡기면 API 키가 없거나 할당량이 소진된 순간 유형 판정 자체가 멈춘다. 이 서비스의 판정 로직은 API 키 유무와 무관하게 동작해야 한다는 원칙(6장)에 따라, 신호 매칭은 정적 사전(`signal_synonyms.json`)으로 처리하고 LLM은 그 위의 보정으로만 남겼다.
- **검증 결과**: 오늘(Day 3, 이번 세션) Playwright로 페르소나 3종을 실행한 결과 각각 3건/2건/3건의 신호가 잡힌다(7장 표 참고).

### b) 동의어 매핑을 추측으로 만들었던 문제

- **발견**: `app.js`의 `PATTERN_SIGNALS` 블록 주석(20~23행)에 "각 항목의 source는 실제 경보 원문에서 확인한 소재를 인용한 것이며(임의로 지어내지 않음)"이라고 명시돼 있다 — 이는 역으로, 그 이전 버전에서는 원문 근거 없이 추측으로 매핑했었다는 뜻이다. 구체적으로 "곧 문을 닫는다며 → 사칭"처럼, 가상자산 페르소나의 표현을 신호 "사칭"에 그냥 붙였던 것으로 보인다(현재 `signal_synonyms.json`의 "사칭" 항목에는 이런 표현이 없다).
- **원인 분석**: 페르소나 시나리오를 신호와 매칭시키는 데 급급해, 문장 표현과 신호명을 의미적으로만 느슨하게 연결하고 실제 경보 원문을 대조하지 않았다.
- **왜 문제인가**: 이 서비스의 신뢰성은 "실제 경보 198건 분석"이라는 근거에서 나온다. 원문에 없는 연결을 마치 데이터 기반인 것처럼 보여주면 근거가 조작된 것과 다름없다.
- **어떻게 고쳤나**: 해당 표현들을 `signals.json`의 데이터 기반 24종에서 분리해, `PATTERN_SIGNALS`라는 별도 카테고리(24~93행)로 옮기고 각 항목에 실제 경보 원문을 그대로 인용했다. 예: "영업종료 사칭"은 2024-28호 원문 "영업종료 가상자산사업자를 사칭한 금전 편취 사기가 성행"을, "단기 고금리"는 2024-14호 원문 "10만원→7일 후 30만원 상환(연10,428.6%)"을 각각 `source` 필드에 그대로 담았다. UI에서도 `signal-chip-pattern` 클래스로 데이터 기반 신호와 시각적으로 구분한다(`renderSignals`, 421~433행).
- **"링크 유도"는 원문에 없어 그 사실을 화면에 명시한 판단**: "링크 유도" 신호의 `source`(85행)에는 "페르소나 문장의 '링크로 들어가서'는 이 소재의 일반화된 표현으로, 알림 원문에 동일 단어가 있는 것은 아님"이라고 스스로 한계를 적어놓았다. 완전히 허구는 아니지만(2024-28호에 "가짜 거래소 홈페이지로 유인"이라는 유사 소재는 있음) 정확히 같은 표현은 아니라는 점을 숨기지 않고 명시한 것이다.
- **검증 결과**: 현재 `PATTERN_SIGNALS` 5종 모두 `source` 필드가 채워져 있고, `signal-chip-pattern`을 hover하면 그 출처가 title 속성으로 노출된다(429행).

### c) 사칭 신호 추가 후 유형이 투자사기로 오분류된 문제

- **발견**: `signals.json`에서 "사칭" 신호는 투자사기 15건, 가상자산 6건, 대출사기 1건으로 압도적으로 투자사기 비중이 높다. 그런데 "사칭"은 세 유형 모두에 등장하는 범용 신호라서, 실제로는 대출사기나 가상자산 상황인데 "사칭"만 걸리면 `signalTotals` 합산 결과 투자사기가 최댓값이 되어 유형이 틀리게 나오는 조용한 오류가 있었다(신호 자체는 맞게 잡혔으므로 겉으로는 "잘 작동하는 것처럼" 보인다는 점에서 더 위험한 오류).
- **원인 분석**: `determineType`이 신호별 `by_type` 건수를 단순 합산만 하고, 문맥(본문에 등장하는 구체적 키워드)은 전혀 보지 않았기 때문이다.
- **왜 문제인가**: 사용자가 대출사기 상황을 입력했는데 투자사기로 잘못 안내되면, 잘못된 확인 카드(제도권 금융회사 조회)를 보여주게 되어 실제로 확인해야 할 것(대부업체 등록 여부)을 놓친다.
- **어떻게 고쳤나**: `determineType`(234~251행)에 "신호 기준 유형과 다른 유형의 일반 키워드가 2건 이상, 그리고 신호 기준보다 우세하게 등장하면 키워드 쪽으로 보정한다"는 로직을 추가했다(`basis: "signal+keyword-correction"`).
- **이후 불필요해진 경위(오늘 세션에서 직접 재현·확인)**: Playwright로 `detectSignals`/`determineType`을 직접 호출해 확인한 결과, 현재 페르소나 3종은 모두 `basis: "signal"`로만 판정되고 `signal+keyword-correction`이 발동하지 않는다. 이유는 (b)에서 추가한 `PATTERN_SIGNALS`(단기 고금리·선입금 요구는 대출사기, 영업종료 사칭·소각 빙자·링크 유도는 가상자산으로 `leanType`이 명확히 지정됨)가 "사칭"의 교차 유형 편향보다 먼저, 그리고 더 크게 해당 유형 쪽으로 점수를 실어주기 때문이다(예: 가상자산 페르소나는 `사칭` 신호 자체가 데이터 기반으로 매칭되지 않고, `영업종료 사칭`·`가상자산 소각 빙자`·`링크 유도` 패턴 신호만 잡혀 가상자산 8점, 나머지 0점으로 판정). 다만 이 보정 로직 자체는 코드에서 제거하지 않았다 — 실제로 "대부업체 직원을 사칭한 사람이 전화로 대출을 권유하며 신용 확인을 요구했습니다"라는 새 문장으로 재현 실험을 하면 여전히 신호만으로는 투자사기(15점)로 잘못 판정되고, 키워드 보정이 이를 대출사기로 되돌리는 것을 오늘 직접 확인했다. 즉 이 로직은 3개 기준 페르소나에는 더 이상 필요 없지만, 그 외 자유 입력에 대한 안전망으로는 여전히 살아 있다.

### d) 확인 카드의 "왜 확인해야 하나"가 전부 동일했던 문제

- **발견**: `buildReason` 함수에 `REASON_BY_TARGET`이라는 확인 대상별 근거 사전이 별도로 존재한다(326~335행) — 이는 이전에 모든 카드가 하나의 공용 문구를 썼다는 뜻이다(현재도 매핑이 없는 대상엔 공용 문구 `"제도권(등록)이 아니면 예금자보호·분쟁조정 대상이 아닙니다."`가 폴백으로 쓰인다, 375행).
- **원인 분석**: 확인 대상(제도권 금융회사, 유사투자자문업자, 가상자산사업자, 대부업체)은 각각 근거 법률과 위반의 성격이 다른데, 초기 구현은 이를 구분하지 않고 하나의 템플릿 문장을 모든 카드에 재사용했다.
- **왜 문제인가**: 카드마다 문구가 똑같으면 "실제 판정 근거"가 아니라 "복사-붙여넣기 템플릿"처럼 보여 신뢰도가 떨어진다.
- **어떻게 고쳤나**: `REASON_BY_TARGET`에 확인 대상별로 서로 다른 법적 근거를 명시했다 — 제도권 금융회사는 예금자보호법·금융분쟁조정, 유사투자자문업자는 투자일임 등 금지행위, 가상자산사업자는 가상자산이용자보호법의 예치금 분리보관·해킹 배상, 대부업체는 이자제한법상 최고금리 초과분 무효·미등록 영업 형사처벌을 각각 근거로 들었다.
- **검증 결과**: 오늘 세션 Playwright 실행에서 페르소나별 확인 카드의 "왜 확인해야 하나" 문구가 서로 다른 법률을 인용하는 것을 확인했다(예: 대출사기 카드 → 이자제한법, 가상자산 카드 → 가상자산이용자보호법).

### e) 확인 대상과 근거 신호가 어긋난 문제

- **발견**: `CHECK_SIGNAL_RULES` 주석(304~305행)에 "이전에는 감지된 신호 중 첫 번째를 그냥 썼음 — 확인 대상과 무관한 신호가 붙는 문제가 있었다"고 명시돼 있다. 사용자가 예시로 든 "신고 여부 카드에 사칭 6건이 근거로 붙는" 현상이 바로 이것이다 — "신고 여부"는 등록/신고 여부를 확인하라는 카드인데 "사칭" 신호(발신자 사칭 관련)를 근거로 대는 것은 논리적으로 맞지 않다.
- **원인 분석**: 확인 카드에 근거 신호를 붙일 때 "감지된 신호 중 아무거나 첫 번째"를 기계적으로 선택했기 때문이다.
- **왜 문제인가**: 확인 대상과 무관한 신호 건수를 근거로 대면 "왜 확인해야 하나" 문구 자체의 논리가 깨진다.
- **어떻게 고쳤나**: `CHECK_SIGNAL_RULES`(306~310행)로 확인 대상 이름의 패턴(`등록|신고`, `제도권|인가`, `진위|발신|매물`)과 그에 맞는 신호 후보(`미신고`/`무인가`, `사칭`, `사칭`/`가짜 거래소`)를 명시적으로 매핑했다. `findSignalCountForType`(314~322행)은 이 후보 목록에서만 근거 신호를 찾는다.
- **검증 결과**: 현재 로직상 "신고 여부" 계열 카드는 `미신고`/`무인가` 신호만 근거로 쓸 수 있어 "사칭" 건수가 붙는 조합 자체가 코드상 불가능해졌다.

### f) 유사 사례가 투자사기 27건 / 대출사기 0건으로 극단적이었던 문제

- **발견**: `renderSimilarAlertsForType` 주석(523~527행)에 겹치는 신호가 없으면 "사례 없음"을 그냥 띄우지 않고 최근 경보로 대체한다는 로직과, 패턴 신호가 alerts.json에 존재할 수 없어 겹침 계산에서 제외한다는 설명이 남아 있다 — 이전 버전은 이 처리가 없어 대출사기처럼 경보 건수 자체가 적은(10건) 유형에서 겹치는 신호 매칭이 우연히 0건이면 유사 사례 섹션이 통째로 비었을 것으로 추정된다. "27건" 같은 구체적 수치는 현재 코드/데이터에서 재현할 수 없어 **미측정**으로 남긴다(git 히스토리가 단일 커밋으로 스쿼시돼 이전 버전의 실제 출력을 재현할 방법이 없다).
- **원인 분석**: 두 가지다. (1) 유사 사례 매칭이 신호 겹침 0건일 때 아무 것도 보여주지 않았고, (2) 패턴 신호(단기 고금리 등)는애초에 `alerts.json`의 `signals` 배열에 없는 이름이라 겹침 계산에 넣으면 항상 0이 되는데 이를 걸러내지 않았다.
- **왜 문제인가**: 대출사기·가상자산처럼 경보 건수 자체가 적은 유형(각 10건)은 신호 겹침이 우연히 없을 확률이 높아, 서비스가 마치 그 유형에 대한 근거 데이터가 없는 것처럼 보이게 된다.
- **어떻게 고쳤나**: `renderSimilarAlertsForType`(528~550행)이 겹침 0건이면 같은 유형의 "최근 경보"로 자동 대체하도록 하고(544~549행), `runAnalysis`(683~684행)에서 패턴 신호를 겹침 계산에 넘기기 전에 데이터 기반 신호만 필터링하도록 했다.
- **검증 결과**: 오늘 세션 확인 결과 페르소나 3종 모두 유사 사례 3건씩 표시된다(7장 표). 대출사기·가상자산도 더 이상 0건이 아니다.

### g) 관련 없는 카드(P2P)가 표시된 문제

- **발견**: `pickChecks` 주석(281~284행)에 "URL도 없고 검증된 탐색 절차도 없는 항목은 관련성이 낮아 기본 카드에서 뺀다 (예: 투자사기의 P2P·해외 비상장주식 — 경보 본문에 확인 방법이라고만 적혀 있고 실제 경로를 이번 조사에서 확인하지 못한 항목)"고 명시돼 있다. `type_profiles.json`의 투자사기 `fine_menu_paths`에는 실제로 P2P 등록 여부, 해외 비상장주식 상장·공시 여부 항목이 `url: "확인필요"`로 남아 있다(69~83행).
- **원인 분석**: 확인 카드를 만들 때 `fine_menu_paths`의 모든 항목을 그대로 노출했기 때문에, URL도 탐색 절차도 확정되지 않은 항목까지 카드로 보여줬다.
- **왜 문제인가**: 사용자가 카드를 보고 확인하러 갔는데 정확한 경로를 모르면("확인필요"), 안내가 아니라 막연한 정보 나열이 되어 서비스 가치를 해친다.
- **어떻게 고쳤나**: `pickChecks`(285~302행)가 URL이 `https://`로 시작하는 확정 항목과, URL은 없어도 `탐색절차` 배열이 있는 항목만 우선 채택하고, 부족하면 신고 전용 항목으로 채운다. P2P·해외 비상장주식처럼 URL도 절차도 없는 항목은 자동으로 카드에서 빠진다.
- **검증 결과**: 오늘 세션 Playwright 실행 결과 투자사기 페르소나는 확인 카드 2개(제도권 금융회사 여부, 유사투자자문업자 등록 여부)만 노출되고 P2P·해외 비상장주식은 나오지 않았다(7장 표).

### h) Gemini 모델 선택 과정 (오늘 세션 1차 근거)

- **1차 시도 — gemini-3.6-flash**: 처음 이 모델로 연동해 페르소나 3종을 반복 테스트하던 중 실제로 429 오류를 받았다. 오류 메시지: `"Quota exceeded for metric: generativelanguage.googleapis.com/generate_content_free_tier_requests, limit: 20, model: gemini-3.6-flash"`, `quotaId: GenerateRequestsPerDayPerProjectPerModel-FreeTier`. **일일 20건 한도**라는 뜻이고, 한 번 소진되면 하루 동안 복구되지 않는다.
- **일일 한도 vs 분당 한도가 결정적이었던 이유**: 같은 방식으로 lite 계열을 테스트하니 오류 메시지의 `quotaId`가 `GenerateRequestsPerMinutePerProjectPerModel-FreeTier`, `limit: 15`로 나왔다 — **분당 15건**. 일일 한도는 소진되면 심사 기간 내내 서비스가 죽을 수 있지만, 분당 한도는 소진돼도 다음 분에 바로 복구된다. 이 차이 때문에 gemini-3.6-flash를 포기하고 lite 계열로 옮겼다.
- **lite 계열 2종 5회씩 실측** (동일 프롬프트, 시나리오 5종, 4.5초 간격):

  | 모델 | 1 | 2 | 3 | 4 | 5 | 평균 | 최대 |
  |---|---|---|---|---|---|---|---|
  | gemini-3.1-flash-lite | 2130ms | 1448ms | 1524ms | 1896ms | 1968ms | 1793ms | 2130ms |
  | gemini-3.5-flash-lite | 1029ms | 1391ms | 1093ms | 1207ms | 1550ms | 1254ms | 1550ms |

- **속도가 더 빠른 3.5-flash-lite를 쓰지 않고 3.1-flash-lite를 택한 이유**: 3.5-flash-lite가 평균 540ms 더 빠르지만, 독립된 두 차례 테스트(페르소나 캐시 생성 시 1회, 위 5회 실측 중 1회)에서 모두 "대출 상담을 **빌미로**"를 "대출 상담을 **빌로**"로 음절을 빠뜨리는 동일한 문법 오류를 재현성 있게 냈다. gemini-3.1-flash-lite는 동일 시나리오를 포함한 모든 테스트에서 이 오류가 한 번도 나오지 않았다. 요약문은 화면에 그대로 노출되는 사용자 대상 텍스트이므로, 400~500ms의 속도 차이보다 문법 오류의 재현성을 더 큰 문제로 판단해 3.1-flash-lite로 최종 결정했다.
- **11.5초 측정값이 1회성 튐이었음을 확인한 과정**: 사용자가 "gemini-3.5-flash-lite 응답 11.5초"를 보고했을 때, 같은 조건으로 5회 재측정했으나 11.5초급 응답은 재현되지 않았다(최대 1550ms). 이전 세션에서 gemini-3.6-flash 자체는 실제로 2~25초+까지 편차가 컸던 것을 직접 관측했으므로(당시 429 소진 전 커밋 확인용 curl 테스트), 11.5초는 네트워크 변동에 의한 1회성 튐으로 결론 내렸다. 다만 재현되지 않았다는 것이 "다시는 발생하지 않는다"는 보장은 아니므로, 타임아웃은 실측 최대치보다 넉넉히 여유를 두었다(아래).
- **타임아웃 9초 → 6초 → 5초 변경 근거**:
  1. 최초(gemini-3.6-flash 사용 시): Netlify Functions 기본 실행 제한(무료/스타터 10초)보다 먼저 우리 코드가 응답을 끝내야 한다는 원칙으로 9초로 설정.

## 6. 안정성 설계

심사 기간 중 서비스가 죽지 않도록 다섯 겹의 방어선을 뒀다.

1. **규칙 기반 단독 동작**: `runAnalysis`(661~685행)는 신호 탐지부터 유사 사례까지 LLM 호출 이전에 전부 렌더링을 끝낸다. LLM 관련 코드는 그 뒤에 이어지는 완전히 별도의 블록이다.
2. **페르소나 캐시**: `persona_ai_cache.json`에 페르소나 3종의 응답을 미리 저장해두고, `findPersonaAiCache(text)`(130~132행)가 정확히 일치하면 API를 호출하지 않고 즉시 반환한다. API 키의 유무와 무관하게 동작한다.
3. **429 조용한 폴백**: `analyze.js`(100~105행)가 Gemini의 429를 감지하면 `{ok:false, quotaExceeded:true}`를 반환하고, 프론트엔드(`renderQuotaNotice`, 611~614행)는 회색 작은 글씨로 "AI 요약은 일시적으로 제공되지 않습니다"만 표시한다. 에러로 보이지 않게, 규칙 기반 결과는 그대로 화면에 남는다.
4. **세션 내 결과 재사용**: `state.llmSessionCache`(Map, 103행)가 같은 입력 문장에 대한 응답을 저장해, 같은 문장을 다시 확인해도 재호출하지 않는다(701~712행).
5. **20자 미만 입력 시 호출 생략**: `MIN_TEXT_LENGTH_FOR_LLM = 20`(108행) 미만이면 LLM을 아예 호출하지 않고 규칙 결과만 남긴다(696~699행).

### 실제 쿼터 소진 상황에서의 검증

오늘 세션 중 gemini-3.6-flash 테스트를 반복하다가 실제로 무료 티어 일일 할당량(20건)을 소진시켰다. 이후 같은 함수를 호출했을 때:

```
curl 결과: {"ok":false}   (HTTP 200)
Gemini 원본 오류: 429 RESOURCE_EXHAUSTED,

```

프론트엔드는 이 상황에서 에러를 띄우지 않고 규칙 기반 결과만 표시했고, 이후 lite 모델로 교체한 뒤에도 429를 모킹한 Playwright 테스트에서 규칙 결과(`type-output`)는 그대로 유지된 채 요약 영역에만 "AI 요약은 일시적으로 제공되지 않습니다"가 표시되는 것을 확인했다(7장).

## 8. 남은 과제

- **배포**: GitHub push, Netlify 사이트 연결, `GEMINI_API_KEY` 환경변수를 Netlify 대시보드에 등록하는 작업이 아직 안 됐다. 로컬 `netlify dev` 검증만 마친 상태다.
- **URL 미확인 항목**: `type_profiles.json`에 `url: "확인필요"`로 남은 항목들 — 투자사기의 P2P(온라인투자연계금융업자) 등록조회, 해외 비상장주식 상장·공시 확인처, 투자사기/대출사기의 불법금융신고센터 정확한 URL, 가상자산사업자 신고 현황 게시물의 직접 URL(kofiu.go.kr 접속 오류로 미확인). 이 항목들은 현재 `pickChecks`가 자동으로 카드에서 제외하고 있어 기능은 안전하지만, 실제로 확인되면 안내 폭이 넓어진다.
- **기능명세서 작성**: 아직 작성되지 않음. 이 보고서의 2~4장이 초안 역할을 할 수 있으나 정식 문서는 별도로 필요하다.
- **테스트 커버리지**: 지금까지의 검증은 전부 수동/스크립트 기반 Playwright 실행이며, 자동화된 회귀 테스트(CI)는 없다. 코드를 수정할 때마다 5~7장의 시나리오를 다시 수동으로 돌려야 한다.
- **`.env` 실키 취급**: 이번 세션에서 실제 `GEMINI_API_KEY` 값이 여러 차례 터미널 로그·curl 명령에 노출됐다(로컬 테스트 목적). 배포 전 이 키를 회전(재발급)하는 것을 권장한다.
- **패턴 신호(`PATTERN_SIGNALS`) 5종의 일반화 검증 부족**: 이 5종은 페르소나 3개의 특정 표현에 맞춰 만든 정규식이라, 페르소나와 다른 표현(예: "장사 접는다며" 같은 동의어)에는 걸리지 않을 수 있다. 자유 입력 검증은 이번 세션에서 몇 개 문장으로만 확인했고 체계적으로 넓혀보지는 못했다.

## 9. 되돌아본 판단

- **키워드 폴백(`KEYWORD_FALLBACK`)의 느슨함**: `투자` 유형에 "코인 수익"처럼 다소 임의적인 2어절 키워드가 섞여 있고, `대출` 유형의 "신용", "한도" 같은 단어는 대출사기가 아닌 일반 신용카드·대출 상담 문의에도 걸릴 수 있다. 페르소나 3개에서는 잘 작동했지만, 오탐(false positive) 가능성을 이번 세션에서 별도로 계량하지 않았다 — 나중에 실제 사용자 입력 샘플이 쌓이면 재검토가 필요하다.
- **PATTERN_SIGNALS의 재현 범위가 좁다**: (8장에서도 언급) 이 5종은 사실상 페르소나 3개의 시나리오 문장에 맞춰 역설계한 정규식에 가깝다. "실제 경보 원문을 인용했다"는 점에서 근거는 있지만, 일반화된 위험 신호 탐지 규칙이라기보다는 "이 3개 예시를 통과시키기 위한" 규칙이라는 성격이 강하다. 새로운 자유 입력에 대해서는 `signal_synonyms.json` 쪽이 더 일반적인 방어선이고, `PATTERN_SIGNALS`는 보조적이라고 보는 게 정확하다.
- **`signal+keyword-correction` 로직이 지금은 죽은 코드에 가깝다**: 5장 c에서 확인했듯 페르소나 3개에는 이 보정이 발동하지 않는다. 합성 문장으로는 여전히 유효함을 확인했지만, 실제 서비스에서 이 분기가 얼마나 자주 발동하는지는 로깅 없이는 알 수 없다. 로깅이 없는 지금 구조에서는 이 보정이 실제로 도움이 되는지, 아니면 불필요한 복잡도인지 판단할 근거가 부족하다.
- **모델 선택 근거의 표본 크기가 작다**: gemini-3.1-flash-lite vs gemini-3.5-flash-lite 품질 비교는 "빌미로→빌로" 오류가 각각 1회씩 나온 것에 크게 의존한다. 5회, 총 10회 남짓의 호출로 내린 판단이라 통계적으로 견고하지 않다. 심사 전에 표본을 늘려 재확인할 여지가 있다.
- **`persona_ai_cache.json`의 정직성 문제**: 캐시에 저장된 문장은 여러 번 재생성한 응답 중 오탈자가 없는 것을 "골라서" 저장한 것이다(문장을 직접 고쳐 쓰지는 않았지만, best-of-N 선택이다). 이것이 "지금 LLM으로 생성한 요약문을 저장하라"는 지시의 취지에 부합하는지는 판단이 갈릴 수 있다 — 오탈자 있는 원본을 그대로 캐시했다면 더 "정직한" 스냅샷이었겠지만, 사용자에게 노출되는 문구의 품질을 우선한 선택이었다. 이 트레이드오프를 여기 명시적으로 남긴다.
- **커밋이 하나로 뭉쳐 있어 이 보고서 자체의 근거가 제한적이다**: 5장 a~g는 코드 주석을 근거로 재구성한 것이지, 실제 diff를 대조한 것이 아니다. 주석이 진실을 정확히 반영한다는 보장은 없다(주석도 사람이 쓴 것이라 과장되거나 생략됐을 수 있다). 앞으로는 작은 단위로 커밋을 나눠, 이런 시행착오 문서를 커밋 로그만으로도 재구성할 수 있게 하는 편이 좋겠다.
